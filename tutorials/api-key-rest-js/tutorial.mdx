## What you will build

Two Node.js scripts with [ArcGIS REST JS](https://developers.arcgis.com/arcgis-rest-js/):

* `create-api-key.mjs` creates the API key credentials and generates the first key, in slot 1.
* `rotate-api-key.mjs` rotates that key without downtime, using the second slot.

Each REST JS function wraps several REST requests; the [REST API tutorial](../api-key-rest/) shows them one by one.

<details>
<summary>Check prerequisites</summary>
<p>An ArcGIS Location Platform, ArcGIS Online, or ArcGIS Enterprise account with a Creator user type or higher and the <strong>Generate API keys</strong> and <strong>Assign privileges to OAuth 2.0 applications</strong> privileges. Ideally a service user with only those.</p>
<p>Node.js 20.12 or later, for <code>process.loadEnvFile</code>.</p>
</details>

</Intro>

## Configure the scripts

Copy `.env.example` to `.env` and fill it in. `.gitignore` keeps it out of your repository.

Every request goes to the portal's <Hint id="sharing-api" label="sharing API">`https://www.arcgis.com/sharing/rest` for ArcGIS Online and ArcGIS Location Platform, `https://<host>/<web-adaptor>/sharing/rest` for ArcGIS Enterprise.</Hint>:

<VarField name="portalUrl" label="Portal URL" placeholder="https://www.arcgis.com/sharing/rest" persist />

The scripts sign in with <Hint id="app-credentials" label="app credentials">Backend jobs can't sign in as you: a username and password don't work with SAML/SSO or MFA. Create the app credentials in the portal as a service user and assign them that user's privileges. They are not the client ID and secret of the API key item the script creates.</Hint>, not as you:

<VarField name="appClientId" label="App credentials client ID" persist />
<VarField name="appClientSecret" label="App credentials client secret" secret />

> **Keep the `client_secret` in a secret manager**, and create the app credentials as a service user with only the privileges these scripts need. With admin privileges, the secret can do almost as much damage as your password.

<details>
<summary>Why the app credentials need their owner's privileges</summary>
<p>Creating and rotating keys with app credentials needs their owner's user privileges: on ArcGIS Location Platform, <code>createItem</code>, <code>generateApiTokens</code> and <code>assignPrivilegesToApps</code> alone were not enough. The secret can't sign in or change your password, but it can do whatever those privileges allow.</p>
<p>In production, the same variables can come from the environment or a secret manager instead of <code>.env</code>.</p>
</details>

</Step>

## Sign in

`process.loadEnvFile()` loads `.env`. `ApplicationCredentialsManager` gets an app token with the client ID and secret, and renews it when it expires.

<details>
<summary>Other ways to sign in</summary>
<p>To sign in as a user, use <code>ArcGISIdentityManager.beginOAuth2</code> (OAuth 2.0) or <code>ArcGISIdentityManager.signIn</code> (username and password).</p>
<table>
<tr><th>Method</th><th>Use it for</th><th>Limits</th></tr>
<tr><td>Username and password</td><td>Trying things on your machine</td><td>Doesn't work with SAML/SSO or MFA accounts; the password ends up in code or the environment.</td></tr>
<tr><td><a href="https://developers.arcgis.com/documentation/security-and-authentication/user-authentication/">User authentication</a> (OAuth 2.0)</td><td>Interactive scripts and apps</td><td>The refresh token expires, and changing the password invalidates it.</td></tr>
<tr><td><a href="https://developers.arcgis.com/documentation/security-and-authentication/app-authentication/">App credentials</a></td><td>Backend jobs, such as scheduled rotation</td><td>They need their owner's user privileges, and the <code>client_secret</code> can do whatever those privileges allow. Both scripts use them.</td></tr>
</table>
</details>

## Create the credentials

`createApiKey` takes the same answers as the [portal's wizard](../api-key-portal/#add-item). Each comment in the code names the wizard screen the option comes from.

<VarField name="privileges" label="Privileges (comma-separated)" placeholder="premium:user:basemaps,premium:user:geocode" persist />

<small>See the [privileges reference](https://developers.arcgis.com/documentation/security-and-authentication/reference/privileges/).</small>

`httpReferrers`, the sites allowed to use the key, is empty so you can test from scripts or Postman.

> **Set your app's URL as a referrer before you ship a public app.** Without one, anyone who copies the key can use it from any site, billed to you. You can't change referrers or the expiration (30 days here) later without invalidating the key.

<details>
<summary>The four requests behind <code>createApiKey</code></summary>
<ol>
<li><code>content/users/&#123;user&#125;/addItem</code> creates the empty item: <code>type=Application</code>, <code>title</code>, <code>tags</code> and the description.</li>
<li><code>oauth2/registerApp</code> registers it with your <code>privileges</code> and <code>httpReferrers</code>, plus <code>appType=multiple</code> and <code>redirect_uris</code>, which come from OAuth 2.0 credentials: the endpoint requires them, but they don't affect the key. It returns the <code>client_id</code> and <code>client_secret</code>.</li>
<li><code>content/users/&#123;user&#125;/items/&#123;id&#125;/update</code> stores <code>apiToken1ExpirationDate</code> in epoch milliseconds. Slot 2 gets <code>-1</code>: no key yet.</li>
<li><code>oauth2/token</code> generates the key: <code>grant_type=client_credentials</code>, <code>apiToken=1</code> and <code>regenerateApiToken=true</code>, because <code>generateToken1</code> is <code>true</code>. On a slot that already holds a key, <code>true</code> replaces it and invalidates the old one at once.</li>
</ol>
<p>Wizard screens: <a href="../api-key-portal/#details">Item details</a>, <a href="../api-key-portal/#item-access">Item access</a>, <a href="../api-key-portal/#register">Privileges</a>, <a href="../api-key-portal/#expiration">Settings</a>, <a href="../api-key-portal/#generate">Generate API key</a>.</p>
</details>

</Step>

## Save the key

`accessToken1` is the key in slot 1. The portal shows it only once: deploy it to your app. `state.json` keeps the item ID and slot for the rotation script, but not the key.

<details>
<summary>Where is the <code>client_secret</code>?</summary>
<p><code>createApiKey</code> removes it from the response. The other functions fetch it from <code>registeredAppInfo</code> when they need it.</p>
</details>

</Step>

## Rotate: start from the key in production

Rotation keeps a valid key at all times: generate a key in the free slot, deploy it, then invalidate the old one.

The script signs in with the same `.env` and reads the item and current slot from `state.json`.

</Step>

## Find the free slot

The new key goes into the slot that isn't in production. Without `state.json`, `slotForKey` reads <Hint id="key-slot" label="the slot from the key">A key ends in `AT1_` or `AT2_` plus eight characters.</Hint>.

</Step>

<Step id="rotate-generate" file="rotate-api-key.mjs" region="rotate-generate" collapsed>

## Generate the key in the new slot

`updateApiKey` sets the new slot's expiration and generates its key. The key in production keeps working.

> **Don't pass `privileges` or `httpReferrers` to `updateApiKey` here.** Changing them invalidates the keys of both slots.

<details>
<summary>REST requests</summary>
<p>An item <code>update</code> with the expiration, then <code>oauth2/token</code> with <code>apiToken</code> set to the new slot. Privileges and referrers would go through <code>{"oauth2/apps/{client_id}/update"}</code>.</p>
</details>

</Step>

<Step id="deploy" file="rotate-api-key.mjs" region="deploy" output="rotate-deploy.txt" view="result">

## Deploy the new key

Put the new key in production. The old key stays valid until you continue.

</Step>

<Step id="invalidate" file="rotate-api-key.mjs" region="invalidate" output="rotate.txt" view="result">

## Invalidate the old key

`invalidateApiKey` with the **old** slot (or old key) invalidates it; passing the new key would invalidate the one you just deployed. The script then saves the new slot to `state.json`.

<details>
<summary>REST request</summary>
<p><code>oauth2/revokeToken</code> with the item's <code>client_id</code>, <code>client_secret</code> and <code>apiToken</code> set to the old slot.</p>
</details>

</Step>
